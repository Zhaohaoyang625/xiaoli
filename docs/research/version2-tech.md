# 小李 2.0 大版本技术可行性调研（2026-08-21）

> 评估对象：情绪化 TTS / Live2D 形象 / 向量记忆检索 / 多模型路由 / 长上下文 / 语音通话模式。
> **硬件前提（重要）**：用户是普通家用电脑（非游戏本），内存按 16G 级别假设，**很可能没有 NVIDIA 独显（或只有核显/集显）**。所有"本地 GPU 推理"类方案都以此为门槛；若机器实际有 ≥6GB 显存的 N 卡，部分方案可从"不现实"升级为"可选"。

---

## 一、情绪化 TTS

### 现状
- 火山引擎豆包语音 v3 SSE 接口（tts_api.py），音色小何2.0（`zh_female_xiaohe_uranus_bigtts`），PCM 直出。
- 已有参数：`speech_rate`（语速）、`loudness_rate`、`post_process.pitch`（音调 -12~12）。**目前没有情绪维度**——生气时声音也是甜的，情绪全靠文案。

### 候选方案
| 方案 | 情绪能力 | 硬件需求 | 可行性 |
|---|---|---|---|
| **A. 火山 emotion 参数** | `additions.emotion` + `emotion_scale`(1~5)。支持值：happy/sad/angry/surprised/fear/hate/excited/coldness/neutral，及 lovey-dovey（撒娇）/shy（害羞）/tender（温柔）/tension（焦急）/comfort（安慰）等 | 云端，零本地成本 | ⚠️ 见下 |
| **B. 火山 TTS 2.0 指令式情绪** | 文本内嵌指令：`<整体情绪：生气，语气：吵架，语速：快>` 或句内 `[急切而发颤]`，模型按指令表现。模型 2.0 级能力，不挑音色 | 云端 | ✅ 首选，需实测 |
| **C. CosyVoice2（阿里开源）** | 3 秒声音克隆、跨语种、情感可控（instruct），中文原生 | NVIDIA 4GB 显存最低（推荐 6GB+）、16G 内存、WSL2 推荐、模型+依赖 10~20GB；纯 CPU 推理 10~30 秒/句 | ❌ 家用机不现实 |
| **D. Fish-Speech** | 提示词情绪标签 `(生气)(喊叫)(耳语)` 等中文指令，中文表现力"开源标杆" | 推理最低 4GB 显存（推荐 8GB）、Windows 原生、模型 4~6GB | ❌ 同上（无 N 卡） |
| **E. GPT-SoVITS** | 台湾腔靠**台湾口音参考音频**复现（5 秒零样本克隆）；情感随参考音频 | 6GB 显存最低（8G+ 推荐）、Windows 整合包一键（20~23GB） | ❌ 同上；且台湾腔要自备台妹音频素材 |

### 关键细节
1. **emotion 参数仅"多情感音色"支持**：多情感音色命名 `*_emo_v2_mars_bigtts`（开心/悲伤/生气/惊讶/恐惧/厌恶/激动/冷漠/中性）。**注意**：这批 1.0 多情感音色已于 **2026-06-30 下线**（官方公告），替代音色在 2.0 系列里——小何2.0 是否属多情感音色、能否接 emotion 参数，**需在体验中心/实测确认**。
2. 指令式情绪控制是 **TTS 2.0 模型的通用能力**（小何2.0 正是 2.0 模型），理论可用且不改音色；但官方标注"2.0 不支持 SSML"，指令格式是方括号/尖括号标记，需实测小何对 `<...>` 指令的响应。
3. 现在的 `speakable()`（voice.py）会清洗掉尖括号/方括号内容——**落地时指令必须加在清洗之后、送进火山之前**，否则被过滤。

### 结论
- **推荐 B（指令式情绪）为主、A（emotion 参数）为辅**：两步都是"改 tts_api.py payload / 文本"级别的小改动，零新依赖、零硬件投入。落地前各用 5~10 句测试文本实测小何2.0 对 `[开心][生气][撒娇]` 指令的实际表现，把"语气指令→小李情绪"映射表（复用 heart.py 的 mood 状态）做好。
- 本地 TTS（C/D/E）在"无 N 卡"前提下全部不现实；**唯一场景**是用户将来有 N 卡后，Fish-Speech 或 CosyVoice2 可作"断网离线备份"，但集成成本高（常驻服务进程 + 热切换）。
- **集成难度：低**（半天级）。TTS 合成对实时链路无影响。

## 二、Live2D 形象

### 现状
- XiaoLi.html：纯 CSS 脸 + 13 种表情（happy/sad/angry/jealous/affectionate/flustered…）+ 打字机 + 本地桥 8800 轮询 face_state.js（2 秒一次）。
- 优点：零依赖、file:// 直接打开就能用；缺点：静态脸，没有动作/头发/眨眼细节。

### 候选方案
| 方案 | 说明 | 集成难度 |
|---|---|---|
| **A. pixi-live2d-display**（推荐） | PixiJS 插件，CDN 一行引入（`cdn.jsdelivr.net/npm/pixi-live2d-display`，npm 包 jsDelivr 可达），支持 Cubism 2.1/3/4（@naari3 分支支持 Cubism 5 + PixiJS v8）。需配 Cubism core（`live2dcubismcore.min.js`，官方直链不稳定，自行托管）。file:// 页面也能加载 https CDN | 中 |
| B. Live2D Cubism SDK for Web 官方 | 官方全套 API，功能最全；API 繁琐、上手慢；授权自 2024-11 起免费（含商业用途） | 高 |
| C. VTube Studio API | Windows 应用 + WebSocket API；要安装并常驻 VTS 程序，适合已有 VTS 的 VTuber，对本地网页集成是杀鸡用牛刀 | 高（环境依赖重） |
| D. 纯 WebGL 手写 | 不现实，工作量一个数量级 | — |

### 免费模型来源（国内网络可达性）
1. **Live2D 官方免费示例模型**（Haru/Shizuku 等，live2d.com 下载）：授权宽松——年营收 <1000 万日元可免费商用，需标注版权声明（"This content uses sample data owned and copyrighted by Live2D Inc."），**禁止色情/暴力/引人不适的呈现**。live2d.com 国内访问可能不稳 → 备选渠道：GitHub 上按官方免费素材协议再分发的镜像仓库，用 jsDelivr 拉。
2. **pixi-live2d-display 自带示例**：仓库 test/assets 含 shizuku.model3.json 等（按免费素材许可再分发）——能过 jsDelivr 拉取。
3. **社区模型仓库**（Eikanya/Live2d-model 等，多为游戏提取模型）：文件多（moc3+贴图+物理），jsDelivr 逐文件拉繁琐；**版权灰色，只能自用不能商用**。
4. **提醒**：Live2D 模型是"多文件目录"结构，file:// 直开页面加载本地模型目录有 CORS 限制——要么模型走 CDN，要么让本地桥（8800）加一个静态文件路由托管模型目录。

### 与 XiaoLi.html 的融合
- 保留现有 CSS 脸做降级兜底（WebGL 不可用时切回），face_state.js 轮询机制**原样复用**——只是 applyState 里把 mood 映射成 Live2D expression/motion，把"正在说话"映射成口型参数（mouth 开合）。
- 现有 MOODS 表 13 种情绪 → Live2D 自带表情（Happy/Sad/Angry 等）+ 自定义 blend 参数。
- 画布层叠在 CSS 脸位置；呼吸/眨眼的 idle motion 由模型自带。

### 结论
- **推荐 A（pixi-live2d-display）+ 官方免费模型**，模型优先用 Shizuku（可爱短发少女，气质接近"小李"人设；Haru 是机器人风不合适）。若拿不到官方模型，再从社区仓库挑"邻家少女"款（自用不商用）。
- **集成难度：中偏高**（1~2 天级）：是六项里工作量最大的一项，价值在"颜值天花板"，不影响任何对话逻辑——可单独排期，失败可完全回退。
- 网络注意：pixi-live2d-display 用 jsDelivr npm CDN；cubism core 建议下载后本地托管（绕过直链不稳）。

## 三、向量记忆检索

### 现状
- memory.py：本地正则提取事实 + bigram/单字启发式打分（≥3 分召回），**代码里明确"向量留待以后"**。
- 局限：近义抓不住——"喜欢喝奶茶" vs "最想喝什么"（共同字"喝"只有 1 分，抓不到）；"他怕黑" vs "晚上睡觉开灯吗"（零共同词，完全漏）。

### 候选：本地中文 embedding 模型（Windows CPU）
| 模型 | 参数 | 磁盘 | 维度 | CPU 单条耗时（i7-12700 实测参考） | 中文 C-MTEB |
|---|---|---|---|---|---|
| **bge-small-zh-v1.5** | 24M | 48~96MB | 512 | **~5.8ms** | 57.8 |
| bge-base-zh-v1.5 | 110M | ~400MB | 768 | ~中等 | 63.1 |
| m3e-base / text2vec-base-chinese | 110M | ~100MB | 768 | ~8.8ms | ~60 |
| Qwen3-Embedding-0.6B | 0.6B | ~1.2GB | 1024 | 可 CPU 跑 | ~62+ |

- **bge-small-zh-v1.5 结论：CPU 上快得无感（毫秒级），内存占用 ~120MB，家用机毫无压力**，不需要更轻的方案（MiniLM 中文没有明显优势，5.8ms 已足够）。
- 模型获取：hf-mirror.com / ModelScope 下载（GitHub/HF 直连不通，走镜像）。
- 依赖：sentence-transformers（会带 CPU 版 torch，安装包 ~200MB+）——或者更轻：直接用 transformers/onnxruntime 裸加载。

### 向量库选型（Windows 安装省事程度）
| 库 | 安装 | 持久化 | 结论 |
|---|---|---|---|
| **纯 numpy 暴力余弦** | 零安装 | 向量 JSON/npy 存本地 | ✅ **当前规模最优**：事实库几百~几千条 × 512 维 ≈ 几 MB 矩阵，一次全量点积 <10ms，无任何额外依赖 |
| chromadb | `pip install chromadb` 一键，零配置 | SQLite 自动落盘 | ✅ 规模上万后无缝升级 |
| faiss-cpu | pip 有 wheel | ❌ 无 CRUD/持久化，要自己管 ID 映射 | 麻烦，不推荐 |
| sqlite-vss | 需预编译扩展/编译，维护已转向 sqlite-vec | SQLite | 最麻烦，不推荐 |

### 对比现有正则召回的提升空间
- 语义级召回（近义/换说法）是实打实的提升点；但对**几百条内的个人档案**，正则+bigram 已覆盖大部分场景，向量带来的增量有限——**价值随事实库增长而放大**（1000+ 条后明显）。
- 推荐**混合路线**：向量召回 top20（模糊语义层）→ 现有重要度/相关度排序 → 取 top5（精确层）。不推翻现有代码，只把 `recall()` 的第一道筛子升级。
- 嵌入计算放后台线程 + 新增事实时增量嵌入，不阻塞对话。

### 结论
- **推荐：bge-small-zh-v1.5 + 纯 numpy 余弦检索（起步）→ chromadb（事实破万后）**。总成本：pip 一个库 + 下载 ~100MB 模型 + 改 memory.py 的 recall。
- **集成难度：低-中**（1 天内）。这是六项里性价比最高的之一。

## 四、多模型路由（深聊 vs 快聊）

### 现状
- 所有请求固定 `deepseek-v4-flash`（config.py）。快，但复杂情感场景（小脾气爆发、哄人、纪念日大场面）时"深度"吃紧。

### DeepSeek 可选模型与价格（2026-08-17 新定价，峰谷分时：高峰 9:00-12:00、14:00-18:00，其余时间半价）
| 模型 | 上下文 | 输入·未命中缓存（空闲/高峰） | 输入·命中缓存（空闲/高峰） | 输出（空闲/高峰） |
|---|---|---|---|---|
| **V4-Flash**（现用） | 128K 原生（可扩 1M） | 1.5 / 3.0 元 | 0.05 / 0.10 元 | 4.5 / 9.0 元 |
| **V4-Pro**（更强） | 同上 | 4.5 / 9.0 元 | 0.15 / 0.30 元 | 13.5 / 27.0 元 |

（单位：元/百万 token。旧名 `deepseek-chat` 仍可用作别名。）

- Pro 比 Flash 贵 **3 倍**（输入）/ **3 倍**（输出）。峰谷分时后：晚上 18 点后、早上 9 点前是半价空闲期——**与"小李"的晚间陪伴场景天然契合，主要聊天时段恰好最便宜**。

### 路由策略建议
- **判定信号（现成）**：heart.py 的情绪值/事件 + 关键词（哄/道歉/吵架/纪念日/生病…）+ 对话长度。
- 规则：日常 → Flash；情绪事件轮（angry≥阈值 / 哄人 / 重要日子 / 深聊话题）→ Pro。深聊占比估 10~20% → 成本增量约 +30~60%，月成本仍然很低。
- 附带收益：Pro 长文表现更好，连珠炮/小脾气剧情的"表演质量"提升，直接服务"真人感"目标。
- **注意**：两模型输出风格可能有差异，路由切换会让"人设一致性"抖动——建议给 Pro 也传相同的系统人设，且只在轮级切换、不在句级切换。

### 结论
- **推荐：上**，规则式路由（不用 LLM 路由，省一层调用）。改动=config 加 PRO_MODEL + chat.py 一行选模型逻辑。
- **集成难度：低**（半天级）。

## 五、长上下文优化

### 现状
- context.py：工作台 = 人设 + 当前时间 + 单层摘要 + **最近 20 轮** + 新输入；超过 20 轮就把最老 10 轮压成一段摘要（COMPRESS_INSTRUCTIONS，3~8 句）。
- 现状已可用，但有两个盲区：① 摘要只保留"事实"，**情绪线/关系事件**（"8/20 吵架和好了""她生日那天我送了什么"）经常被压掉；② 模型全系 **128K 原生上下文**（可扩 1M），现在 20 轮才用 ~10K token，**空间大量浪费**。

### 优化空间
1. **放宽轮数**：20 → 60 轮（≈30K token）。成本几乎为零：输入未命中 1.5 元/百万 → 每次请求 ~0.05 元，命中缓存后 0.05 元/百万。
2. **分层摘要（当前单层 → 三层）**：
   - 层1 滚动对话摘要（现状保留）；
   - 层2 关键事实清单（与 memory.py 档案记忆互补，谁/哪里/喜恶——已存在，把摘要里重复的部分去重）；
   - 层3 **情绪/关系线**："（8/20 因提别的女生吵架→哄好；最近常撒娇要陪）"——一行字就能让小脾气剧情跨轮延续。
3. **关键句原文保留**：程序判定（情绪事件/重要信息）的轮次不摘要、直接存原文，比摘要损失小。
4. **缓存友好（重要发现）**：DeepSeek 服务端自动硬盘缓存，命中价 = 未命中价 1/10~1/50，但**要求请求前缀字节级稳定**。现有结构（人设→时间→摘要→历史）前缀已比较稳定；进一步优化：把"【现在的时间和日期】"从第二条 system 消息**挪进最后一条 user 消息里**，让人设+摘要+历史成为纯稳定前缀 → 前 N-1 轮每次都命中缓存。压缩时保证历史字节不变。
5. **睡前总结**：现有夜间静默/主动说话机制里加"睡前把今天聊的收进摘要"——摘要时机更自然，比聊天中挤压更省。

### 结论
- **推荐：上**。核心改动=context.py 的 build_workbench（轮数+分层+时间戳位置）+ compress（三层摘要）。
- **集成难度：低-中**（1 天内）。成本几乎不变，记忆连续性明显提升。

## 六、语音通话模式（VAD 自动检测→说完即答）

### 现状
- 链路（已打通）：点🎤按钮 → 火山流式 STT（音量 peak>500 + 安静 1.0s 自动停）→ LLM → TTS 整句合成完再播。用户实测"说完约 1~2 秒就有回应"。
- 已有积木：`stop_playing()` 可随时打断播放；`proactive.set_recording()` 防抢话门控；TTS 首包时延火山实测 ~700ms（业界一流）。

### 可行性分析
- **完全可行，且不是重写而是"现有组件重组"**。缺的只有两块：
  1. **常开监听线程**：麦克风持续开，VAD 检测"开口/闭嘴"。候选：**silero-vad**（1.8MB 模型、CPU 每 30ms 帧 <1ms、`pip install silero-vad`，Windows 无压力）——比现在的音量阈值准得多：噪音环境不误触发、喘气/咳嗽不误判。断句静音时长 550~800ms（比现在的 1.0s 更利落）。
  2. **打断 + 门控**：VAD 检测到用户开口且她在说话 → 立即 `stop_playing()`（已有）；播放期间 VAD 不触发识别（半双工门控，避免自己的声音被录进去——**回声消除**是家用场景的最大坑，真做全双工需 WebRTC AEC；先做播放门控的半双工，简单可靠）。
- 时延预算：VAD 10ms + STT 流式 ~150ms + LLM 首 token ~100ms + TTS 首包 ~700ms ≈ **1 秒级**；人类感知：>1.5s 才觉得故障，1s 内"开口即答"体验已经很好（行业内 400ms 是流水线级全双工目标，顺序式架构到不了，也没必要为家用场景强求）。
- 可选增强：火山**双向流式 TTS（WS v3）**首包更快（配 `use_segment_cache` + `seed-tts-2.0-standard`，支持 `section_id` 多轮会话）→ 把"收完整包再播"改成"首包即播"，再省 300~500ms。改造量中等（tts_api 加流式回调 + 播放侧边收边播），可排二期。

### 对比"按说话"按钮
| | 按钮模式（现状） | 通话模式（VAD） |
|---|---|---|
| 操作 | 每句点一次🎤 | 说就行，全自动 |
| 误触发 | 无（用户主动） | 环境噪音/自言自语可能误触发（VAD 调参可压） |
| 自然度 | 打断式 | 连续对话，接近打电话 |
| 实现 | 已完成 | 常开监听 + VAD + 门控 |

### 结论
- **推荐：上**，做成可切换模式（按钮保留当"确定模式"兜底，HTML 加"🎙 通话模式"开关）。一期：silero-vad 替换音量阈值 + 常开监听 + 播放门控（1~2 天）；二期：流式 TTS 边收边播。
- **集成难度：中**。风险点集中在 Windows 声卡行为（麦克风格式/延迟）和 VAD 误触发调参，其余全是现成积木。

## 总表：六项候选可行性结论

| 项 | 结论 | 成本 | 集成难度 | 一句话理由 |
|---|---|---|---|---|
