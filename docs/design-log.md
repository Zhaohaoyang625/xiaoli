# 小李项目 · 设计日志

> 每个机制的"怎么设计的、考虑到什么、学习了什么"都记在这里。
> 这是项目设计的完整档案：为什么这样做、为什么不那样做。

## 设计原则（贯穿全程）
1. **仿真真人**：一切以"像活人"为验收标准
2. **App 是游戏主持人**（学自 UTSUWA）：状态由程序管，LLM 只能建议
3. **壳层为王**：价值在机制不在模型
4. **记忆在硬盘**：任何对话窗口都不是记忆载体
5. **本地优先**：能本地算的不调 API（省钱+稳定），学自 MISS MemoryScorer
6. **优雅降级**：LLM 失效时程序照常工作（学自 UTSUWA/MISS）
7. **不做操纵**：不挽留、不PUA（学自 HBS 实证警示）

## A.1 文字对话 + 双轨引擎（已完成）
- **双轨**：inner_thought（内心真实想法）vs spoken（说出口的话）
- **学自**：MISS `<cognitive_engine>`——双轨放在提示词层而非代码层，让模型自然模拟两种思维
- **考虑过**：代码层分拆双轨（重、不自然）→ 否；提示词层（轻、改人设即改逻辑）→ 选
- **需求来源**：用户需求清单（恋人闺蜜混合/直接热恋/软甜撒娇/吃醋真生气型）

## A.2 上下文管理（已完成）
- **工作台/日记本**：模型上下文=工作台，本地文件=日记本
- **学自**：MemGPT 三层记忆思想 + UTSUWA 记忆预算
- **参数**：最近20轮（UTSUWA 默认10-20轮区间取上限）；压缩每次10轮
- **时间戳**：每条消息带时间并**嵌入文本**（教训：API 会丢自定义字段，看不见的字段等于不存在）
- **时间推理**：规则并入人设（教训：第三条 system 消息 flash 不重视）；2026说大二→2027自动大三 ✅实测通过

## B.1 情绪层"心"（已完成）
- **结构**：mood(情绪+强度+causes最近5个) + affection(0-100) + last_interaction
- **学自**：UTSUWA MoodState 带因果 + 时间衰减 + 启发式基线；MISS 的"本地评分不花API钱"
- **时间衰减**：48h好感衰减(每天-1,上限10)；72h心情变忧郁(强度每天+5,上限30)；每次离开只衰减一次
- **启发式**：正面+2/负面-1/深度话题+2/提问+1（本地关键词，LLM 不给建议时兜底）
- **LLM 建议钳制**：情绪白名单12种；好感±5封顶（学自 UTSUWA：畸形建议不能破坏状态）
- **教训**：可选字段 flash 会省略→必填（没变化填0）✅实测通过

## B.2 主动互动层（已完成）
- **机制**：①一天4次主动节奏窗口（早安7-9/午间11-13/傍晚17-19/睡前21-23，每天每窗口一次）②提醒机制（她说出 [reminder:5min] 标签 → 程序定时器 → 到点触发）③错过浮现（关机期间到点的提醒，开机时出现）④<event> 层触发（不伪装用户消息）
- **学自**：UTSUWA 提醒机制（reminder 标签+定时器+错过浮现）+ <event> 事件层；节奏表来自 docs/interaction-rhythm.md（Pew 85%每日联系期望、一天4次节奏、不轰炸）
- **关键原则**：机器回合不推进关系（主动说话不改好感不改心情，UTSUWA）；她主动说过的话记进日记——她自己得记得自己说过什么
- **实测教训**：①flash 会省略闭合标签（[/reminder]）→ 正则兼容无闭合（内容到下一个 [ 或结尾，零宽断言避免吞掉下一个标签）②flash 偶发空输出 → call_xiaoli 重试2次 ③LLM 不会自发用标签 → 人设教她 + **程序兜底**（用户请求含"提醒/叫我"关键词时注入提示）——"App是游戏主持人"：机制不能只靠 LLM 自觉
- **测试**：单元16项（标签解析/到期只触发一次/错过浮现/窗口每天一次/调度器）+ 端到端4连测（答应提醒→到点主动说话→不推进关系→重启记得）✅

## B.3 档案记忆层（已完成）
- **机制**：①提取——LLM 输出 new_memory 字段（必填数组）+ 本地正则兜底（"我叫…""我喜欢…"等8类模式，抓到"他叫小明"这种第三人称事实）②存储——data/facts.json（content/category/importance/confidence/createdAt/lastRecalled）③检索——本地打分（共同bigram×2+有效单字×1，≥3分召回，按重要度取top5），向量检索留待以后 ④老化——7天没提重要度-1，降到0遗忘删除
- **学自**：MISS MemoryScorer（本地评分不花API钱 + 记忆老化）、UTSUWA 三层记忆（贴身/档案/聊天）、mem0（记忆有重要度/置信度/时间戳）
- **考虑过**：jieba 分词 → 不装库（bigram 打分够用）；向量库 → 本地优先原则留待以后
- **实测教训**：①bigram 只做"字面重复"检索，"想喝什么"vs"喜欢喝奶茶"0重叠 → 加单字打分 ②LLM 提取的"宝贝喜欢喝奶茶"（带称呼）与本地"他最喜欢喝奶茶"内容近似不重复 → 两条都在，近似去重可接受
- **测试**：单元20项 + 端到端4连测（提取→新会话凭档案记得→本地兜底→老化）✅

## C 语音层（已完成 → 2026-08-20 火山路线升级）
- **第一版方案**：edge-tts（微软免费TTS）台湾女声 zh-TW-HsiaoChenNeural（晓臻），语速 -5% 更软糯；pygame 播放 mp3
- **为什么先选 edge-tts**：免费、台湾腔原生、实测连微软服务通畅（对比：CosyVoice 要 GPU 和模型下载，本地跑不动；GPT-SoVITS 要录音训练，复杂度高）→ CosyVoice 列为后续进阶
- **用户实测反馈（两次）**：①晓臻"一个字一个字读、人机感强"→ A/B 对比 6 个音频确认是**声线质量问题**（微软台湾声线逐字慢读）；②换晓晓后自然多了但普通话无台湾腔，仍"挺像人机" → 结论：免费微软声线天花板有限
- **升级方向调研**：2026 年 TTS 格局——火山引擎中文第一（1.3元/千字）、MiniMax 情感最强（8情感）、CosyVoice 开源但需GPU；参考 Open-LLM-VTuber（开源AI伴侣标杆）其 edge-tts 实现与我们相同（代码实证），高质量路线靠本地引擎或商业API
- **用户决策（AskUserQuestion）**：走**付费API路线（火山引擎）**，先用自带音色（"甜美台妹"BV025_streaming 免费音色，参考音频克隆留待以后）
- **最终方案**：tts_api.py 调火山**新版 v3 接口**（`openspeech.bytedance.com/api/v3/tts/unidirectional/sse`，SSE 流式，音频分片 base64 拼接；鉴权 = `X-Api-Key` 头 + `X-Api-Resource-Id`，**新版控制台没有 AppID 体系**）→ voice.py 合成优先火山，**降级链：火山 → edge-tts 晓晓**（未配置/失败自动回退，静默不打断对话）
- **正式音色（用户实测选定）**：**小何2.0** `zh_female_xiaohe_uranus_bigtts`（2.0服务免开通直接可用）
- **音色实测教训（重要，省了一下午弯路）**：①旧版"甜美台妹"BV025_streaming 在新版接口无效（资源不匹配）②音色后缀决定资源：`*_uranus_bigtts` → seed-tts-2.0（已开通），`*_moon_bigtts` → seed-tts-1.0（需另开通"语音合成1.0"）③湾湾小何（疑似台湾腔）即使开通1.0也报"requested resource not granted"——音色级单独授权，未解决 ④vivi2.0 最像真人但无台湾味；柔美女友/甜美悦悦偏软不够自然；**体验中心试听是选音色的正确姿势**（API 试错太慢）⑤新版 API Key 不能用于旧版 v1 接口（Authorization: Bearer; 后报 grant not found）
- **播放**：Windows 原生 mci（ctypes winmm.mciSendStringW）替代 pygame —— 实测 pygame/SDL 播 mp3 有"逐字顿挫"（用户反馈的元凶之一）
- **优雅降级**：语音失败绝不打断对话（合成失败 → 静默回文字）
- **控制权**：启动 `python chat.py --voice` 开启；运行中"语音开/语音关"随时切换
- **学自**：火山官方示例 agentkit-samples/byted-text-to-speech（gh-proxy 抓取验证请求格式）；Open-LLM-VTuber（语音+形象一体化思路）
- **后续可选**：湾湾小何授权排查、声音克隆（用户找到参考音频后）、CosyVoice 本地

## C.5 语音输入层（STT，2026-08-20 新增）
- **用户需求**："想直接和他对话，而不仅仅通过打字" → 说→识别→进对话
- **方案**：火山引擎**流式语音识别2.0**（与 TTS 同账号同 Key，免费20小时/年额度）——stt.py：sounddevice 录音（静音1.2秒自动停）→ SAUC 二进制帧协议推流 → 增量文本
- **录音库实测教训（一整个下午的坑）**：①pyaudio/PortAudio 在"英特尔智音技术"麦克风上**所有设备恒定峰值255**（占位静音，老驱动兼容问题）②waveIn（winmm）只有 1 个映射器设备且无数据（Win11 新版音频栈架空老 API）③**sounddevice（自带新 PortAudio）立即可用**（峰值32767）→ 录音库定为 sounddevice；wavein_rec.py 保留为备用（2026-08-20 整理时移至 tools/wavein_rec.py）
- **协议实测教训**：①`format` 合法值是 pcm/wav/ogg/mp3（传 raw 被断连）；采样率字段是 `rate` 不是 sample_rate ②**所有包必须 Gzip 压缩**（官方示例如此，不压被断连）③请求帧不带序列号，音频结束用最后一块 flags=0x2(LastPacket)（不是 Positive/NegativeSequence——那是旧版协议）④发包间隔必须 100~200ms（连发断连）⑤`language` 参数仅限流式输入模式（nostream），双向流式(bigmodel_async)不传 ⑥响应 `result` 是**字典**（text 在 result.text，逐帧增量变长），最后 flags=3 帧是完整结果（definite=true）——取最后一帧，别拼接
- **mp3 直传识别无效**（返回空 result）→ 音频必须转 16k PCM 再传
- **集成**：chat.py 输入「说」→ stt.listen_once() → 识别文本当作你说的话走完整对话流程 → 她语音回答。声音进、声音出。
- **实测**：录音 ✅ 识别 ✅（"今天好累哦，我想喝奶茶"）端到端待用户验收
- **血的教训（2026-08-20）**：给 listen_once 加录音标志时**误删了函数最后的 `return last_text.strip() or None`**——识别一直成功但返回值永远是 None，网页显示"没听清"、用户以为"她听不到"（实际她听到了，是代码没递出去）。排查过程：mic_check（设备✅）→ stream_check（流式✅）→ STT_DEBUG 调试开关（打印显示"最后文本='今天天气不错哟。'"但返回 None → 定位到缺 return）。**教训①编辑删除代码段时确认完整函数语义②听不到问题时先查"返回值有没有真的回来"**。STT_DEBUG 调试开关保留（$env:STT_DEBUG="1" 时打印详细过程，平时无输出）

## E 特殊日子：生日/节日（2026-08-20 升级）
- **用户需求**："她认识今天是什么日子吗" → 生日/节日当天主动送上祝福
- **方案**：special.py 三层结构 —— ①节日表：公历固定节日（元旦/情人节/520/儿童节/国庆/平安夜/圣诞/跨年）+ **农历节日**（春节/元宵/七夕/中秋/重阳，用 lunardate 库算，清华镜像 pip 可装；库缺失自动跳过农历，不影响运行）②他的生日：聊天中"我生日是9月15号"类说法 → 本地正则提取（必须带"生日"关键词防误报，如"12月我要去考试"不提取）→ 存 data/birthday.json（**单独存**，不走 facts 记忆老化，她永远不会忘记你生日）③每天只主动触发一次（data/special.json 记 fired 日期，重启不重复）
- **挂载方式**：proactive.Scheduler._tick 增加第3步检查（节奏窗口/提醒/特殊日）→ 复用 handle_event 主动说话链路（机器回合不推进关系）；跨天运行时零点自动触发，无需重启
- **LLM 提示**：check_today 拼描述"今天是情人节，也是他生日（2月14日）"→ <event> 块进 prompt，她自然发挥（实测输出："寶貝～情人節快樂，也是生日快樂啦！…"双节日不搞混）
- **生日提取双通道**：用户说的话 + LLM new_memory 记忆里都可能带生日，chat.py 都扫一遍
- **测试**：test_special.py 10项（提取防误报/存储/公历农历检查/每天一次/调度器链路）
- **顺手修的测试脆弱性**：①test_b2 的提醒测试用真实时钟，晚上跑会额外触发"下班问候"窗口 → 改固定时间 ②test_b2_e2e 断言繁简不兼容（"开会"vs"開會"）→ 兼容 ③e2e 提醒测试 LLM 偶发不输出标签 → 加最多3次重试（与 chat.py 空输出重试同思想）
- **她主动问生日（2026-08-20 用户追问"记忆难道不是对话获取的吗"后补上）**：生日未知时，每隔 3 天（ASK_INTERVAL_DAYS）找机会主动问你——Scheduler._tick 第4步检查 should_ask_birthday（生日已知→永不问；未问过→问；距上次问≥3天→再问），事件消息提示她"找个自然的方式撒娇问他"。实测效果："我们在一起这么久，我好像还没问过你生日是哪一天捏？偷偷告诉我嘛…"。你说的生日 → extract_birthday 记住 → 自然不再问。test_special.py 相应加 5 项测试（含调度器链路）

## F 主动找话题（2026-08-20 用户需求："开启聊天后她也能自己向我说话，我再回复她"）
- **用户原话**："现在是我和他说话他回复我，每次我都要找话聊，能不能我开启聊天后他也能自己向我说话我再回复她"——即对话发起权不全在用户手里，像真人聊天有来有往
- **v1 方案（用户说"不像真人"已推翻）**：90 秒死板计时器到点必开口 + 15 分钟防轰炸。用户反馈："这个我感觉就不太像真人，那我说完话之后他应该是有一个判断接下来是继续我来开话题，还是他有什么想说的，有什么想说的话他思考一下就说出来了"
- **v2 方案（当前）**：**"开口机会"式**——互动计时器放宽到 **3 分钟（IDLE_MIN_ACTIVITY_SECONDS=180）** 且两次机会隔 **15 分钟（MIN_IDLE_CHAT_GAP_SECONDS=900）**；到点不是"必须说话"，而是给 LLM 一次机会："主动权在你：有特别想说的就自然说出来；没有就安静陪着"。**说或安静由 LLM 判断**（实测教训：死板计时器是"程序替她决定"，判断式是"她自己的决定"，后者才像人）
- **v3 方案（用户澄清"3分钟是保险"后，2026-08-20）**：用户原话——"我想的是在她每次回复我时也要判断要不要和我主动找话题聊，而3分钟是一个保险，就是必须她主动找话聊"。双层结构：**日常**=她每轮回复后自己判断要不要延续话题（persona continuation 从"憋得慌才写"改为"每次回复完都要判断，想聊就写，不话痨不硬撑"）；**保险**=3分钟到点**必须**主动找话（事件消息改为"作为女朋友，你现在应该主动找他聊"，LLM 没说出口 → **程序兜底话术** proactive.IDLE_FALLBACK_LINES 6句软话随机顶上——保险必须有声）。测试 83 项全过
- **v4 方案（用户实测"说完话不会继续找话说"后，2026-08-20）**：用户最终预期——"他能主动找话说，说了一句还有一句两句好几句，就是他自己能说下去，不需要我一直说"。三处升级：①**continuation 改数组**（1~3条，一句句停顿说出；persona 说明从"可选"改"必填"——实测教训：可选字段 flash 会省略，必填（没想聊写 []）才稳定输出）②**keep_talking 字段**（必填 true/false）：她回复后判断"还想不想继续说"→ true 则程序等 8 秒（KEEP_TALKING_WAIT_SECONDS），你没接话她就**再主动说一轮**（最多 3 轮 KEEP_TALKING_MAX_ROUNDS，真人也会说累了停下）；你说过话 → 时间戳（mark_user_speak）检测，她立即收声不再抢话（**教训：不能用 _interrupted 判断——主循环会复位它，keep_talking 线程会误判**，用"等待区间内用户是否说过话"时间戳）③parse_reply 兼容字符串/数组/空。测试 83 项 + 2 e2e 全过
- **v4 实测教训（"她好像三句话一起说的"）**：continuation 句间停顿固定 1 秒太短——她语速快/内容连贯时听起来像连珠炮一次说完（用户预期是"一句、想一想、再一句"的节奏）。修复：句间停顿改 **1.5~2.5 秒随机**（`random.uniform(1.5, 2.5)`，真人没准点；也兜住了 TTS 播放失败时 `played.wait()` 立即返回的场景——失败路径下句间也有停顿感）。节奏三要素：停顿要够长、要随机、放在每句播放前（含主话→第一句补话之间）
- **v4 实测教训②（"他是不是每次都会说3句话，这不像真人"）**：用户点破根因——**真人说话的频率取决于"为什么还要继续说"，不是固定几句**。用户原话给出真人的三问："上句话我没说完？（→ 接着把话说完）""用户不理他？（→ 先想为什么，再决定要不要开口）""用户不太会说话？（→ 她找话题来带）"。此前 continuation"必填 1~3 条"被 flash 理解成"必须填满"→ 每轮固定三连击，反而没人味。修复三层：①**persona 写进三问判断逻辑**——continuation 只在"自己话没说完/想追问接话"时写，**明确"大多数回复都写 []"**（真人说一句等一句，只有话痨才每句补两三条）；"冷场了"归 keep_talking 管，不靠 continuation；keep_talking 增加**开口前先想他为什么没说话**（在忙？没话题？不知道咋接？）②**示例 JSON 改成常态**（continuation: [], keep_talking: false）——模型以模仿示例为默认，示例满编它就满编 ③**程序兜底**：continuation 截断最多 2 条（`[:2]`），即使模型话痨也不会三连击。教训：**"必填防省略"和"默认少说话"要一起教**——字段必填是保结构，默认值要示范"常态是闭嘴"

- **研究**：3 组并行（产品组 CAI/星野/Replika/哄哄模拟器/PTT 台语 / 角色卡组 SillyTavern spec+代码+官方卡 / 状态机组 UTSUWA/SynthMind/ZifaMem 实际下载读码）→ 全文 docs/research/personality-temper.md
- **用户拍板 4 决策点**：触发=提别的女生/前女友+一整天不理她；生气上限=会软化不真不理（2~8 轮）；"靠北喔"只在生气峰值一次（PTT：整天靠北反而假）；翻旧账=撒娇式偶尔提
- **已就位的机制**（之前版本）：EMOTIONS 含 angry/jealous、detect_temper（强/弱触发+排除词+哄词）、apply_temper（吃醋→连续触发升级 angry→哄降级→两次哄心软）、气不过夜（12h 自动消）、RELATION_MOODS 钳制、persona 小脾气节+3 示例段、网页 angry/jealous 表情
- **本次补的**："一整天不理她"（apply_time_decay：24~72h 没互动→重逢酸溜溜 jealous，72h+ 被 melancholy 忧郁覆盖——失落比吃醋更重）；final_e2e 场景7.5 小脾气全链路（吃醋→升级→哄→和好 4 项检查）
- **e2e 实测暴露 3 个程序钳制缺口（核心教训）**：
  1. **解包 bug**：`apply_temper` 返回 `(heart, event)`，chat.py 直接 `temper_event = apply_temper(...)` 把整个元组当 event——`kind` 拿到 heart 字典（永远不是 "jealous"）→ 💔 提示永不显示。改 `_, temper_event =`
  2. **程序状态被 LLM 自报覆盖**：吃醋轮 LLM 自报 sad → 覆盖程序 jealous → 下一轮"再提→升级 angry"检测不到（当前不是 jealous 走不到升级分支）
  3. **和好闭环被 LLM 自报破坏**：被哄时 LLM 自报 angry +20 加深（每轮叠加抵消哄的 -25）或报 neutral 覆盖降级状态 → "哄两句就心软"永远达不到
- **最终规则（heart.py merge_llm_suggestion）**：**程序判定轮（temper_event 存在：本轮吃醋/哄好）→ 情绪状态程序独占**，LLM 只演（话怎么说）不自报（状态怎么变）；非程序轮 LLM 自由自报（补充通道：程序关键词覆盖不到的"放鸽子/被凶"由 LLM 补上）。游戏主持人原则贯彻到底：**关系事件的"是什么"归程序，"怎么演"归 LLM**
- **测试**：test_b1 新增 4 项（24h 吃醋/23h 不触发/3天忧郁覆盖/和好防回退/吃醋轮锁状态），全量 115 项单元 + 17 项 e2e ✅

## L 验收实测修复（2026-08-20 用户实测 4 个反馈）
1. **连珠炮还在**：用户"第一句说完一两秒就说第二句第三句" → 根因：continuation 上限 2 条（主话+2补=3句）+ 句间停顿 1.5~2.5s 太赶。修复：上限 [:2]→[:1]（主话+1补正好，真人很少一口气连说 3 句）+ 停顿 2.5~4s（"想了想再补一句"的间隔感，比普通句间停顿长）
2. **提醒没触发（用户实测"30秒后提醒我喝水"没响）**：根因不是计时，是**解析器正则 `(\d+)` 只认整数，LLM 写的 [reminder:0.5min] 含小数点 → 整条标签被静默丢弃**——用户求了提醒、LLM 也写了标签，程序却没收到（静默失败最坑：两边都不知道哪出错了）。修复：正则支持小数+秒单位（0.5min=30s / 30sec）；trigger_at 改秒级精度（"%H:%M:%S"，30 秒提醒要准）；get_due 兼容旧分钟格式数据；e2e 场景5 手写 trigger_at 同步秒格式
3. **提醒标签还是概率性漏**（e2e 场景4 一次 0 条）：长上下文下 flash 2 次重试仍全漏 → 重试 2→3 次 + 提示加示例格式（"[reminder:30min]该吃药了[/reminder]"）+ 注明 30 秒写 0.5min——flash 跟格式写命中率高很多
4. **3 分钟没主动不是 bug**：用户测试时 23 点，夜间静默 22-8 点生效（用户自己拍板"假装睡了"）——白天才主动
5. **"一整天不理她"不用电脑一直开机**：apply_time_decay 在启动时算"上次互动→现在"的差值，关机期间也算
- 测试：117 项单元（+2：0.5min/30sec 解析）+ 17 项 e2e 全过

## M 做作修复 + 情绪驱动说话量（2026-08-20 用户："我把这个分享给我女同学，她说很做作" + "说话句数不该被限死，说完一句再判断要不要说下一句"）
- **两个反馈一起治**：
  1. **"很做作"**：女同学"也说不上来，可能就是台湾甜美的语言比较做作" → 诊断：**24 小时都在"甜"是根因**（甜腻+语气词密度是"做作感"的来源）。修复=**甜度分层**（persona 性格节）：平时正常聊天像普通台湾女生（语气软但不腻、重点是接得住话），开心/被哄/想他/撒娇要东西时才甜度拉满——**"甜是调味料，不是主食"**；语气词降密度（啦/喔/捏/齁 一两句带一次，别每句都带）；撒娇不刻意（心情好才来一两句）
  2. **说话量情绪驱动**：用户"一条说完再说一条，句子不该被限死，说完一句再判断要不要说下一句；真人生气会连珠炮弹说好多控诉，声音愤怒最后带哭腔" → 上一版（L 节）为了治"三连击"把上限砍到 [:1]+2.5~4s 停顿——**方向错了**：真人是"平静时一句等一句、激动时连珠炮"，不该一刀切
- **修复（三层）**：
  1. **continuation 上限放宽** [:1]→[:3]（防失控保险：最多主话+3 条，不会无限）；**停顿情绪驱动**（_say_continuations）：angry/jealous/sad/anxious/melancholy/excited → 1~1.5s 连珠炮（越说越急的感觉）；其他 → 2.5~4s 想了想再说
  2. **persona 教法**：continuation 节改写"说多少由情绪决定"——③情绪激动写 3~4 条连珠炮（生气控诉/超开心连说/委屈倾诉），大多数回复写 []（平静时连说 2-3 条=话痨）；新增【示例：她气炸了连珠炮的样子】（他提女同事→她第1句翻旧账"上次也说坐一下…"、第2句"你回她消息回得比回我快"、第3句"行啊你去啊…我回我妈家住几天"）；小脾气节真生气改"话一句接一句地控诉他（连珠炮）冒台湾气话，气到后面带委屈（呜…）"
  3. **程序注入（关键一役）**：describe 加生气分级（强度低→嘴硬话短；70+→连珠炮）后 e2e 实测**升级轮 LLM 还是只回一句阴阳怪气**（"喔～周日呀…你去吧，我没事啦"）——描述层教法被长工作台淹没（flash 遵循弱）。**游戏主持人原则再延伸：程序检测 angry 强度 ≥70 → 消息末尾注入【情绪指令·必做】**（离输出位置最近、遵循率最高）。第一版注入 spoken 变控诉了但 continuation 仍 []（**先例效应：上下文里 LLM 自己上轮的 [] 输出格式被模仿**）→ 第二版把结构钉死："spoken 只写第一句短控诉，其余全部写进 continuation 数组（2~3条，每条15~25字），先翻旧账→再控诉现在→委屈收尾，禁止把话塞进 spoken 一句"。实测出连珠炮：spoken"喔～那你慢慢想啊，人家才不在意咧。"→ continuation ①"哼，她约你你就心动齁？"②"你上次也这样，跟别的女生吃饭回来还跟我说只是同事！"③"呜…你要去就去啊，反正我就在家等你，看你几点回来……"——翻旧账/越说越气/委屈收尾全齐，keep_talking: true 连上
- **注入点**：chat.py 主循环 messages 组装后（facts_block 之后、提醒兜底之前）+ final_e2e user_turn 同步（同路径）
- **测试**：test_b1 42 项 + test_b2 40 项 + final_e2e 17 项全过；快测验证连珠炮 3 条结构（脚本已删）
- **M.2 连珠炮间隔再修（用户复测："一句刚开始说一两秒就开始说下一句，不是一句话说完后再说下一句"）**：第一版情绪驱动把激动停顿设成 1~1.5s（"连珠炮越说越急"），被用户点破——真人吵架是"一句一句往外蹦"，**连珠炮感来自每句都短、持续控诉，不是间隔 1 秒的机关枪**；间隔太短 = "上一句还没说完下一句就抢着说"的错觉（实际播完回调没问题，就是 1~1.5s 停顿太短）。修复：激动 2.0~3.0s（说完一句缓口气再蹦下一句）、平静 3.0~4.5s（想了想再说）。教训：情绪驱动 ≠ 激动就压短停顿，间隔下限 2s 才能建立"说完了一句"的感知（用户抱怨线在 1~1.5s）
- **M.3 双声重叠修复（用户复测："一句话说到一半就又有另一个开始说下一句话，两个声音都在说话"——根因不是停顿，是两条播放链并发）**：连珠炮场景 LLM 都写 keep_talking:true → `maybe_continue_talking` 在她刚开口（主话还没播完）就开后台线程倒计时 5 秒 → 主话 3~4s + 连珠炮补话 6~10s 还没播完，5 秒就到了 → 她"再主动说一轮"的新回复插进来播 → 上一句还在播，两个声音重叠（用户听成"说到一半就有另一个开始说下一句"）。修复=**`_round_done` 事件门闩**：`say_with_continuation` 开头 clear（这轮开始说话），`_say_continuations` 结束（finally，含被打断路径）set（这轮全部说完），`continue_talking_loop` 在 sleep 等待前 `_round_done.wait()`——keep_talking 的 5 秒从"她全部说完"才开始计时（顺带修掉了"keep_talking 间隔从回复开头算"的既有偏差）。play_speech 全路径（成功/失败/静默）都走 on_done → 无死等风险。门闩语义快测通过（播放中不放行/说完全放行/顺序无重叠，脚本已删）
- **M.4 双声并发根因（用户复测："第一个人刚开始说大概两秒后又有第二个声音，第一句话还没说完"）**：M.3 门闩只解决了 keep_talking，没解决**另一条并发链**——Scheduler 线程的主动事件（节奏窗口/闲聊/提醒/特殊日/出门跟进）与主循环回复播放完全无互斥：事件的话 TTS 合成（~2 秒）期间用户回复正好在播，合成完直接插进来 → 听到"第一句还没说完第二个声音就来了"（MCI 单 alias 切换时旧音频尾巴+新开头，听感=双声）。**修复=说话流互斥锁 `_speak_guard`**（同一时刻只允许一个说话流），按优先级三档：
  - **用户回复**（say_with_continuation(..., _interrupt=True)）：stop_playing 打断正在播的（含提醒）→ acquire 等让位（被打断后 ~0.1s 释放）→ 播
  - **提醒**（_wait=True）：不打断，等当前流说完再响（提醒必须响，错过触发数据就丢了）
  - **主动事件/keep_talking**（默认）：acquire(False) 失败 → 让位跳过（Scheduler 下个 tick 会再触发，不丢）；handle_event 开头还加 locked() 提前检查省 API 钱（正在播就别调 LLM 合成）
  - 锁释放：say_with_continuation 的 _finish 闭包（_say_continuations 结束后 finally release，hold_lock 捕获避免 voice_on 中途切换导致锁不配对）
  - 验证：mock 播放快测（回复播中主动事件让位/提醒等完再响/锁释放后正常播，全过，脚本已删）；117 项单元 + 17 e2e 全过
- **M.5 语音双声最终根因（用户第 4 次复测："第一句话还没说完第二个声音就来了"→ 用户问"我们现在这个语音到底是怎么说的"）**：前三次修复（停顿/门闩/互斥）都对但不彻底——**真正的根因在播放器层：mci 的"播完检测"跨线程不可靠**。诊断过程（真 TTS 实测时间线）：①手动 mci open/play/status 轮询（同线程）→ 播放完整（3.86s 才 stopped）②play_speech（status 在 _wait_done 线程轮询）→ **播放 0 秒就 on_done**（mciSendStringW 是 Windows 消息驱动接口，跨线程查询 status 立即失败 → mode 空 → break → on_done 提前）→ 连珠炮下一句在上一句刚开始播时就插进来 → 用户听到"第一句话还没说完第二个声音就来了"。**换播放方案：火山 TTS 直出 24k PCM（format: "mp3"→"pcm"，零解码）+ sounddevice（PortAudio，跨线程安全）播放**：sd.play + sd.wait 在播放线程内完成，播完才 on_done，时序精确。降级路径（edge-tts mp3）用 miniaudio 解码成 PCM 同播（pip 清华镜像）；pygame 解码验证有"时长翻倍"bug（SDL_mixer 对 24k mp3 按 48k 解码）弃用；mci/pygame 播放退役。打断：sd.stop() → sd.wait() 返回 → on_done（实测 0.2s）。**验证：串行 3 句连珠炮每句完整播完才回调（3.8s/5.3s/4.4s，之前 0.26s 就提前）**；117 项单元+17 e2e 全过。教训：音频播放"播完"检测的可靠性是"一句说完再说下一句"的前提——选跨线程安全的播放库，别赌 MCI

## S Live2D 落地：七连坑 + 本地化终局（2026-08-22，O1 收尾）
**结果**：紫色小人 shizuku 显示成功，会呼吸摆动眨眼。最终方案 = 全本地化 + 本地 http 服务器。
**七连坑按序（每个都有用户实测证据）**：
1. **cubismcore 官方 CDN 403**（live2d.com 国内不可达）→ jsDelivr npm 代理 live2dcubismcore@1.0.2
2. **模型 @0.4.0 分支路径 404** → 改 master 分支（master 的 shizuku 是 Cubism2 格式）

**变速三轮试听，最终结论：不变速（2026-08-22 深夜）**：
